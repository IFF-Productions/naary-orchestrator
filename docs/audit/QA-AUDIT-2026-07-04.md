### Q-1 (Medium) — Verify interpreter control-flow node coverage before trusting it

**What exists (confirmed by filename):** activity specs for `agent`, `code`, `http`, `mcp`, `rss`, `sendEmail`, `signing` (hmac/jwt), `sql`, `totp`; DSL resolver specs for array-nodes (filter/aggregate/listOps), branch, canonical, http-request, rename-keys, respond-webhook, rss, send-email, set, signing, sql-query, sub-workflow, walk; interpreter e2e (`interpreter.e2e.spec.ts`, `branching.e2e.spec.ts`) and `error-sanitization.spec.ts`.

**Gap to verify:** the *interpreter-level* `execNode` branches for the durable/control-flow node types — `merge` (fan-in join), `forEach` / `executeSubWorkflow` (child fan-out + depth cap + cost metering), `wait` (timer), `humanApproval` (signal + timeout auto-reject), `stopAndError`, and `continueAsNew` boundaries — are the highest-risk, least-obviously-covered paths. The DSL specs test the *pure resolvers*, not the interpreter's orchestration of them. Before relying on these, confirm `interpreter.e2e.spec.ts` actually exercises:
- a `merge` where branches arrive in both orders, and the **stranded-join → `invalid_graph`** path (`workflows.ts:815-823`);
- a `forEach` over an **empty array** (`:563`) and one that **exceeds `MAX_FOREACH_ITEMS`** → `circuit_open` (`:568`);
- `humanApproval` **timeout auto-reject** (`:691-698`) and the signal path;
- the **depth guard** (`:492`, `:559`) via a self-referential graph;
- a **`continueAsNew`** boundary preserving `ctx`/`costUsd`/`stepCount`/`mergeArrivals`.

**Why it matters:** these are the durable-execution differentiators. A regression here (e.g., a merge that silently completes without firing) fails *silently* as a "completed" run. Recommendation: if any of the above is not asserted, add it — these are the specs most worth having.

### Q-2 (Medium) — `respondToWebhook` await is poll/timing dependent

**Where:** `apps/api/src/executions/executions.service.ts:280-319` (`startWebhookAwaitResponse`).

The synchronous-response path polls the workflow `webhookResponseQuery` every `pollMs` (150ms) until a 10s deadline, using real `setTimeout` and `Date.now()`. This is correct by design (the response is set fast, before any long-run `continueAsNew`), but it's inherently a race between the poll loop and the worker setting the response. Under a loaded worker or slow CI, the run may set the response *after* the deadline and the ingress falls back to 202 — a legitimate outcome, but one that makes any e2e asserting a specific synchronous body **flaky**.

**Recommendation:** in the e2e for `respondToWebhook`, assert on *either* the response body *or* the 202 fallback + eventual run state, not solely the body; or raise `timeoutMs` for the test. Confirm `apps/web/e2e/new-nodes.spec.ts` (or wherever this is exercised) doesn't hard-assert the body under a tight deadline.

### Q-3 (Low) — `forEach` fan-out can overshoot the per-execution cost cap

**Where:** `apps/worker/src/temporal/workflows.ts:577-609`.

All children in a `forEach` batch are launched with the **same** `childCap = perExecutionCapUsd - costUsd` snapshot and run concurrently, so up to `MAX_FOREACH_ITEMS` (100) children can each spend up to the remaining cap before any of their costs are metered back into the parent. Aggregate spend can exceed the per-execution cap by a bounded-but-large multiple. This is acknowledged in the code comment as the "same class as the documented monthly-cap overshoot," and it is bounded (100× cap worst case), so Low — but for a tenant with a meaningful cap and a wide fan-out it's a real overspend window.

**Recommendation:** document the overshoot bound explicitly in the budget UI, or divide the remaining cap across the batch (`childCap / items.length`) as a coarse guard. Add a test asserting the documented bound.

### Q-4 (Low) — Merge fan-in join relies on deterministic `Promise.all` arrival order

**Where:** `apps/worker/src/temporal/workflows.ts:744-756`.

The fan-in join counts arrivals (`mergeArrivals`) as branches reach a merge node under the parallel `Promise.all` fan-out (`:794`), and only the last arrival runs the merge. Correctness *and replay determinism* both depend on the interleaving of concurrent `execChain` branches being identical on replay. The code comment argues this holds because "arrival order under the fan-out is fixed by microtask/activity-completion order, which Temporal replays identically" — which is true for activity-driven branches, but is subtle enough to be worth an explicit regression test.

**Recommendation:** ensure a determinism-replay e2e includes a diamond graph (fan-out → two branches with activities of differing latency → merge) so any future change that breaks replay-stable arrival order is caught. If such a test exists in `interpreter.e2e.spec.ts`, this is already covered — verify.

### Q-5 (Low) — Billing edge-cases not re-verified this pass

Prior QA#2 (cached input tokens double-billed) and QA#3 (activity retry re-calls the LLM and double-writes usage) live in `runAgent` (`activities.ts:866+`) and the usage ledger, which I did not read in depth this pass. CLAUDE.md's hard rule 6 (billing must fail safe; never record zero on missing usage) and its warning about `result.usage` vs `result.totalUsage` make these worth a dedicated re-check. Prior QA#13 (spend aggregation reads all rows into memory) is in `packages/usage` / `apps/api/src/usage` — also not re-verified.

**Recommendation:** a focused follow-up on `runAgent` billing + `usage.service` aggregation, asserting: (a) missing `usage` → fallback estimate, not zero; (b) `totalUsage` (not `usage`) is what's recorded; (c) a retried activity doesn't double-write the ledger; (d) aggregation is a SQL `SUM`, not an in-memory reduce.

### Q-6 (Info) — CI gating

**`.github/workflows/ci.yml`** gates **typecheck + test + web build** on every `pull_request` and push to main — a solid required gate. It uses `on: pull_request` (not `pull_request_target`), so fork PRs can't exfiltrate secrets; a dummy `.env` satisfies the prisma-generate wrapper (generate never connects); the suite mocks `@naary/db` so no live Postgres is needed.

**`.github/workflows/e2e.yml`** runs the Playwright stack on a **self-hosted** runner, correctly fork-gated (`github.event.pull_request.head.repo.full_name == github.repository`) so untrusted fork code never executes on the runner. It's a *separate, non-blocking* job by design — a flake there won't block the proven verify gate.

**Gap:** because e2e is non-blocking, a real e2e regression can merge if reviewers don't check it. That's an intentional trade-off; just be aware the "required" quality bar is the `verify` job, not the browser stack.
